# Что другие приложения, устройства и файлы могут сделать с хранилищем

**Статус:** закрыто 2026-11-26. Поводом стал отчёт о подделке синхронизационных фантомов
в чате. Здесь такой уязвимости нет: устройства синхронизируются через synced FS
платформы, фантомов и входящей почты нет. Аудит проверил другие пути, по которым
чужие данные попадают в Storage.
**Тесты:** `tests/unit/deno/picker.service.spec.ts`, `tests/unit/gui/risky-file.spec.ts`,
`tests/unit/gui/pdf-thumbnail-scale.spec.ts` и дополнения в спеках `dialog-capabilities`,
`request-params`, `save-collision`, `validate-filename`, `fs-service.restore`,
`fs-service.delete`, `index.rpc`, `favorites.service`, `app-config.service`,
`listing-xattrs`, `drag-and-drop`, `entity-name`, `logger`.

## Откуда приходят чужие данные

- **Другие приложения через file picker.** Storage реализует системные файловые диалоги
  (`capImpls` `w3n.shell.fileDialogs.*` в манифесте), поэтому их вызывает любое
  установленное приложение. Заголовок, подпись кнопки, `defaultPath` и фильтры пишет
  вызывающий. Picker отдаёт ему файлы и папки, в том числе на запись.
- **Свои же устройства и приложения с доступом к userFS.** Они пишут имена файлов,
  xattrs (метки корзины `parentFolder`/`originalName`, `thumbnail`, `tags`, `id`)
  и файл избранного в synced-хранилище приложения.
- **Перетаскивание извне.** Текст, брошенный в окно из браузера или другого приложения.
- **Сами файлы:** их открывают в ОС, по ним строятся превью (PDF, изображения).

## Правила

| Что | Правило | Где |
|---|---|---|
| Выбор папки в picker | корень хранилища не отдаётся. Раньше «открыть папку» без выделения отдавала текущую папку, а picker открывается в корне Home. Подпись кнопки задаёт вызывающий, поэтому один клик по «Open» давал ему весь Home (корзину тоже) или корень устройства на запись. То же «Use folder» в `saveFolder` | `folder-operations.ts` (`isFsRootPath`, `openFolderTarget`), `usePickerConfirmState.ts`, `usePickerDialogActions.ts` |
| Запросы к picker | один за раз: пока диалог открыт, следующий запрос отклоняется. Второй запрос на том же соединении заменял режим, тексты и ответ диалога на экране, например «открыть файл» превращался в «открыть папку» под той же кнопкой | `dialog-capabilities.ts` (`beginDialogRequest`) |
| Тексты вызывающего | заголовок — одна строка до 200 символов, подпись кнопки — до 40. Управляющие, bidi- и zero-width символы заменяются пробелом. `defaultPath` длиннее 1024 символов или со скрытыми символами отбрасывается. Фильтров не больше 50, расширений не больше 100 на фильтр, каждое до 32 символов. Заголовок на desktop обрезается многоточием | `request-params.ts`, `file-picker-dialog.vue` |
| Имя по умолчанию в picker | скрытое имя (с точки в начале) не предлагается: так нельзя подставить `.trash-folder-…`. Пользователь может ввести его сам | `default-save-location.ts` |
| Сервис для picker | отдаёт только хранилища видимых корней (те же настройки, что у списка корней), а не все шесть как `WritableFS`. Список папки — только для видимого хранилища, по безопасному пути, вне корзины, без xattrs | `src_deno/services/picker.service.ts` |
| Открытие файла | исполняемые и запускающие скрипты файлы (список как в Inbox и Chat) и имена с bidi-символами открываются только после подтверждения. Для ссылки проверяется и имя цели. Раньше любой синхронизированный или присланный `.sh`, `.command`, `.html`, `.exe` уходил обработчику ОС по двойному клику | `src/utils/risky-file.ts`, `fs.store.ts` (`openFile`) |
| Drop в окно | копируются и перемещаются только сущности перетаскивания, начатого в приложении: они берутся из store. Текст события drop не читается. Раньше JSON `{fsId, value}` из любого брошенного текста запускал copy/move произвольных путей, в том числе из device FS (например `~/.ssh` в общую папку). Комментарий в коде утверждал обратное | `useFsDnD.ts`, `run-mode-info.store.ts`, `drag-and-drop.ts` (`entitiesOfDrop`) |
| «Восстановить с заменой» | цель восстановления из меток корзины не может быть корзиной или лежать в ней: папка внутри корзины заменяется корнем, а сама корзина как цель — отказ. Конфликтующий элемент перемещается в корзину под свободным именем (`a_<время>.txt`), а не стирается. Сервис возвращает, куда он ушёл (`RestoreResult.replaced`), и пользователь видит уведомление «заменённый объект перемещён в корзину: "a.txt" как "a_….txt"». Без него новый файл в корзине выглядел как переименованный восстановленный. Раньше метки (их пишет любое устройство или приложение с доступом к userFS) позволяли навсегда стереть корзину, сам восстанавливаемый элемент или любую папку | `prepare-restored-path.ts`, `restore-fs-entities.ts`, `fs.store.ts` (`notifyAboutReplacedEntities`) |
| IPC `restoreEntities` | только сущности внутри корзины, режим только `keep`/`replace` | `src_deno/index.ts` |
| Удаление | «навсегда» решается для каждой сущности по `isSameOrInside`, а не по префиксу первой. Пакет из корзины и не из корзины отклоняется. Корень и сама корзина не удаляются | `delete-fs-entities.ts` |
| Имя корзины | из `config.json` берётся, только если это допустимое имя, начинающееся с `.trash-folder-`; иначе — имя по умолчанию. `saveConfigFile` не меняет имя корзины | `app-config.service.ts` (`isValidTrashFolderName`) |
| Файл избранного | ошибка чтения не останавливает сервис: избранное считается пустым, файл не перезаписывается, пока пользователь его не изменит. Берутся только записи `{favId, fsId, fullPath}` из строк, ключ равен `favId`, путь безопасный, не больше 1000. Так же при слиянии конфликта. Раньше битый файл синхронизировался и на каждом устройстве при запуске вёл к `closeSelf()` | `favorites.service.ts` (`checkedFavoritesData`, `loadFavoritesFileData`) |
| xattrs в списке и в свойствах | `thumbnail` — data URL растрового изображения до 256 КБ (раньше без лимита), `id` и `ext` — до 64 символов, `tags` — до 100 строк до 128, `sync`/`hidden` — до 64. В свойствах сущности `id` и `tags` проверяются так же, как в списке | `listing-xattrs.ts`, `load-folder-content-list-prepared.ts`, `load-fs-entity-stats.ts`, `THUMBNAIL_MAX_LENGTH` |
| Превью PDF | длинная сторона canvas не больше четырёх целевых размеров. Размер страницы задаёт автор PDF, и страница 1 × 14400 pt давала canvas любой высоты | `pdf-actions.ts` (`pdfThumbnailScale`) |
| Новые имена | при создании и переименовании (GUI и deno `renameEntity`) имя не начинается с точки (иначе оно пропадает из списка) и не содержит C1-управляющих символов, bidi-переопределений, U+200B и BOM. ZWJ/ZWNJ разрешены: они нужны эмодзи и некоторым письменностям. Существующие имена проверяются по-прежнему. Picker не принимает имён с bidi-символами | `entity-name.ts` (`isValidNewEntityName`, `hasSpoofingCharacters`), `validate-filename.ts` |
| Логи | переводы строк и управляющие символы в сообщении экранируются: один вызов — одна строка. Имя с `\n` с другого устройства подделывало строки лога | `shared/utils/logger.ts` (`oneLine`) |

## Проверено, изменений не потребовало

- **HTML.** В `src` и `src-file-picker` нет `v-html`. Единственный `v-ui3n-html`
  выводит статическую строку i18n, `innerHTML` — статическую разметку ошибки запуска.
  Диалоги, уведомления, подсказки и редактируемые имена выводят текст через mustache
  или `value`. Ни имена файлов, ни тексты вызывающего picker не попадают в HTML.
- **Иконки и превью в `src`/`url()`.** Только `data:image/(png|jpeg|gif|webp|bmp);base64,…`
  без SVG, кавычек и скобок. SVG-файлы показываются через `<img src="blob:">`, где
  скрипты не исполняются.
- **Ссылки** создаются из объектов, которые вернул файловый диалог, а не из строк путей.
  Разрешение ссылок ограничено `MAX_LINK_HOPS`, копирование не следует по ссылкам.
- **Загрузка из ОС** пишет с `exclusive`, для `file-type` читает сэмпл 4100 байт,
  превью строит для файлов до 30 МБ. Хеширование потоковое.
- **Экспорт в ОС** не перезаписывает существующее.
- **Синхронизация** принимает удалённую версию только в состоянии `behind`, конфликты
  отдаёт пользователю. `pre-initial-clean` удаляет только фиксированный файл.
- **IPC.** Вызываются только перечисленные методы. Тестовых хуков в IPC нет. xattrs из
  GUI пишутся по белому списку.
- **Зависимости.** fflate нет. pdfjs-dist 6.5 содержит исправление CVE-2024-4367 и
  больше не использует `eval` (опции `isEvalSupported` в нём нет). Предупреждение
  сборки о `eval` относится к сгенерированному protobuf-коду
  `shared/utils/ipc/ipc-service-caller.js` (`eval('require')` с фиксированной строкой).
- **Picker.** Пути из `defaultPath` и введённые имена уже проверялись. Открытие
  файла отдаёт `ReadonlyFile`. Новые файлы и папки создаются с `exclusive`, перезапись
  идёт только после подтверждения. Корзина исключена из корней. `appFS` приложения
  в picker не попадает.

## Что не меняли

- **Права в манифесте.** По коду не используются `storage.*` у GUI и обоих picker (FS
  приходят по IPC) и `appRPC` у deno-компонента. Снимать их можно только после проверки
  на платформе, что FS-объекты, полученные по RPC, работают без собственных
  storage-caps.
- **Перезапись файла в save-диалоге** отдаёт вызывающему `WritableFile`, а через него
  чтение старого содержимого и, возможно, версий (`v`). Это семантика платформы.
  Пользователь подтверждает перезапись в диалоге.
- **Экспорт имён с `\`, `:`, `CON` и подобными на device FS Windows** зависит от того,
  как платформа пишет такие имена. Если подтвердится, это дефект платформы.
- **Временные строки лога 🔗** с путями на уровне info
  (`link-aware-fs.ts`, `sync.service.ts`) нужны для отладки синхронизации через ссылки
  (живое тестирование, раунд 2). Их нужно убрать вместе с завершением этой отладки.
- **CSP в `index.html` нет.** Сейчас нет и HTML-вывода данных, при котором он бы
  понадобился.
- **Аргументы `AppStorageInternal`** проверены частично. Сервис доступен только окну
  самого Storage (`thisAppComponents`).
