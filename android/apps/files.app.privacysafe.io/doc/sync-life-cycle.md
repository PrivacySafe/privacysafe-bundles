# Жизненный цикл синхронизации

Описывает очередь синхронизации пользовательского synced-хранилища: [src_deno/services/sync.service.ts](../src_deno/services/sync.service.ts).
Синхронизация файла избранного устроена отдельно, см. [favorites.service.ts](../src_deno/services/favorites.service.ts).

## Элемент очереди

Очередь — это `Map` с ключом-путём. Ключи всегда нормализованы через `formatPath`: `'/a'`, `'./a'` и `'a'` — один и тот же элемент. Корень хранилища — `''`.

| Поле | Смысл |
|---|---|
| `status` | `pending` — ждёт обработки; `inProgress` — для него идёт действие |
| `attempts` | число неудачных попыток подряд; после `MAX_ATTEMPTS` (3) элемент не обрабатывается |
| `lastError` | текст последней ошибки |

Статус `inProgress` держится только пока реально идёт действие: загрузка завершается событием `upload-done`. Любой другой исход возвращает элемент в `pending` или удаляет его из очереди.

## Старт

1. Очередь читается из файла `sync-queue.data` в app local FS. Элементы, сохранённые как `inProgress`, переводятся в `pending`: после перезапуска ни одно действие этого процесса не идёт. Для элементов, исчерпавших попытки, планируется повтор (см. «Ошибки»).
2. Состояние связи определяется одним запросом к серверу, дальше его обновляют наблюдатель `w3n.connectivity` и ошибки соединения в самих вызовах синхронизации.
3. Если связь есть — выполняется стартовое сканирование: корень и объекты корневого уровня в состоянии `unsynced` или `behind` попадают в очередь. Если связи нет — сканирование выполнится при первом её появлении (и повторится, если упадёт).
4. Подписка на события дерева (`watchTree('')`). При ошибке наблюдателя он подписывается заново с нарастающей задержкой (1 с … 60 с), а элементы `inProgress` перепроверяются: их `upload-done` мог прийти, пока наблюдателя не было.

## Постановка в очередь

Изменяющие RPC-методы (`index.ts`: создание папки, копирование, перемещение, переименование, удаление, восстановление, xattrs, избранное) вызывают `addSyncQueueItem` для изменённых объектов и их родительских папок. При удалении в очередь ставится и папка, из которой удалён объект, — иначе другие устройства продолжат его видеть.

`addSyncQueueItem` при наличии связи планирует проход (`planSync`, задержка 500 мс). Очередь сохраняется в файл с задержкой 1 с, но не реже чем раз в 5 с при постоянных изменениях.

## Проход по очереди

Одновременно идёт только один проход. Запрос `planSync`, пришедший во время прохода, не теряется: сразу после текущего прохода запускается следующий.

1. `expandParents` достраивает иерархию: если в очереди есть `a/b/c`, туда добавляются `a/b`, `a` и `''`.
2. `getReadyToSyncList` выбирает элементы `pending` с `attempts < 3`, у которых нет прямых потомков в очереди, — самые глубокие первыми. Родитель синхронизируется только после всех своих детей.
3. Для каждого элемента (`handleSyncStep`):
   - элемент переводится в `inProgress`, запрашивается `status(path)`;
   - объекта больше нет (`notFound`) — элемент удаляется;
   - идёт загрузка (`uploading.uploadStarted`) — элемент остаётся `inProgress` до `upload-done`;
   - `synced` и потомков в очереди нет — элемент удаляется;
   - иначе выполняется действие по состоянию:

| Состояние | Действие |
|---|---|
| `unsynced` | `startUpload`. Вернул задачу — ждём `upload-done`. Вернул `undefined` (загружать нечего) — элемент удаляется |
| `behind` | `adoptRemote` с удалённой версией. Успех — элемент удаляется. Затем для файлов до 3 МБ, всё ещё находящихся в состоянии `behind`, запускается скачивание (`actionAfterAdopt`; срабатывает ли это условие после adopt — не проверено на живой платформе) |
| `conflicting` | событие `arose:conflict` в GUI, элемент удаляется из очереди (см. «Конфликты») |
| `synced`, но в очередь успели попасть потомки | элемент возвращается в `pending` и ждёт их |

4. Проход останавливается, если пропала связь: ошибка соединения в `status` или событие наблюдателя. Это не считается неудачной попыткой; элементы `inProgress` возвращаются в `pending`, и их подхватит проход после восстановления связи.

## Завершение загрузки

На `upload-done` статус объекта проверяется ещё раз. Если он снова `unsynced` — объект изменили во время загрузки — элемент остаётся в очереди и загружается снова. Иначе элемент удаляется. На `download-done` элемент удаляется.

## Удалённые изменения

События `remote-change` и `remote-removal` с состоянием `behind` ставят объект в очередь: принятие удалённой версии идёт тем же проходом — по одному и от детей к родителям. С состоянием `conflicting` — в GUI отправляется `arose:conflict`.

## Ошибки

Ошибка действия (`startUpload`, `adoptRemote`) увеличивает `attempts`, возвращает элемент в `pending` и планирует проход через 2 с. После 3 неудачных попыток подряд:

- в GUI отправляется `sync:error`;
- элемент больше не обрабатывается и, оставаясь в очереди, не пускает в синхронизацию своих родителей;
- через 10 минут счётчик сбрасывается и элемент получает новую серию попыток. Повтор планируется и при старте приложения для элементов, сохранённых с исчерпанными попытками.

## Конфликты

Конфликтующий объект удаляется из очереди и не блокирует родителей: иначе один неразрешённый конфликт остановил бы синхронизацию всей ветки вплоть до корня. Сам конфликт хранится платформой в состоянии объекта: строка в таблице показывает его и даёт открыть диалог разрешения. Отдельно GUI открывает диалог для конфликтов корня и корзины.

## Действия из GUI

GUI может напрямую вызвать `startSyncUpload`, `startSyncDownload` и `startSyncAdopt` (диалог разрешения конфликтов, кнопки в строке). Индикаторы прогресса в GUI, не получавшие событий дольше 2 минут, скрываются; элементы очереди GUI не удаляет — их жизненным циклом управляет только Deno-сервис.
